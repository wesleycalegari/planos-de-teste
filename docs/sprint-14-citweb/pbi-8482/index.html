2. Descrição

Defeito (causa raiz confirmada pelo dev): em Domain/InterfaceStreitiDomain.cs, método EfetuaCarga (linhas 452–492), o fluxo real de processamento estava desativado (comentado) e substituído por um bypass de teste marcado //TIRAR SE FOR TESTAR CARGA, que insere uma linha nova em tb_itf_smx_ctl_prc_dui a cada carga, sem verificar registro existente para a mesma DUIMP. Como a exclusão de pacote apenas remove o registro de controle do pacote (tb_itf_smx_ctl_pct_str) — fazendo o sistema "esquecer" que o pacote foi recebido — e o WI Quorum devolve sempre a mesma lista, cada ciclo exclusão→recarga duplicava todas as DUIMPs do pacote.

Fix entregue (task #8484, branch fix/ADO-8482-duimp-bypass-teste-duplica-registro):

  • Inserção idempotente — guarda de existência antes de gravar em tb_itf_smx_ctl_prc_dui (recarga não duplica);
  • Fluxo real reativado — bypass removido, ProcessaDUIMP volta a executar;
  • Lock por número de DUIMP (ObtemLockControleDuimp) — serializa ler-status → processar → gravar no mesmo processo (mitigação da issue High de concorrência do gate da PR #1758; constraint de unicidade no banco ficou como follow-up separado).
Dimensão do problema no HML vigente (medido em 03/09/2026, SQL read-only na base smt-hom-citweb-axa): 12.978 linhas para 2.477 DUIMPs distintas (~5,2 linhas por DUIMP); pior caso com 27 linhas. A DUIMP de rastreio usada pelo dev tem 14 linhas nessa base — 5 antigas (out/2025) + 9 inseridas por recargas entre 28/08 e 02/09/2026, uma por carga — demonstração viva do defeito no ambiente vigente. O fix ainda NÃO está deployado no HML vigente: a validação do dev (01/09) foi com build local apontando para a base alfa (ambiente descontinuado).
