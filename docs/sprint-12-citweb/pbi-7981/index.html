CONTEXTO — estado atual do CITNET medido no código (07/08/2026)

O rótulo do campo já promete o M — Tipo Documento (C/M/O) — e a view declara quatro opções estáticas:

CitNet2/Views/AverbacaoNacional/AverbacaoRCV.cshtml (l. 159-165)
  X = Selecione...

Mas o que a view declara é irrelevante depois que a apólice carrega. O JS reconstrói o combo do zero:

CitNet2/Scripts/averbacao-rcv.js (l. 2167)
function montarTipoDoc(tipoApolice, nfeObrigatorio) {
    $("#e_doc_ebq :gt(0)").remove();        // apaga TODAS as opcoes menos "Selecione..."
    if (tipoApolice == "E" && nfeObrigatorio == "S") {
        append N;  val N;  disabled         // NFe forcada e travada
    } else {
        append C;  append O;                // <<< so CTE e Outros — o N NAO entra
    }
}

Três consequências que moldam este plano:

  1. O fix precisa tocar dois pontos — a view e o montarTipoDoc. Mexer só na view faz a opção sumir ao carregar a apólice. Foi exatamente isso que o #7980 teve de resolver no CITWEB, e a orientação de arquitetura daquele card diz literalmente: "sem isso a opção some ao carregar apólice". Por isso o CT-TDC-001 confere o combo depois de apólice + subgrupo, não ao abrir a tela.
  2. A descrição do card contradiz o código. Ela afirma que hoje o combo "lista apenas CTE, Nota Fiscal Eletrônica e Outros". Medindo: no caminho normal o combo efetivo tem só CTE e Outros. O N aparece apenas quando a apólice é tipo E com NFe obrigatória — e aí vem forçado e desabilitado. Isso vira o CT-TDC-002.
  3. O fix do CITWEB acrescentou N junto com M (// #7980 — inclui MDF-e (M); NFe permanece disponível no ramo 59). Se o CITNET acrescentar só o M, os dois sistemas divergem no N — e o CA deste card pede os quatro.

⚠️ Contradição do card já decidida — validação do número do MDF-e

O CA deste card pede: "ao informar um número de documento MDF-e fora do padrão esperado, o sistema deve avisar o usuário, da mesma forma que já faz hoje para CTE e Nota Fiscal Eletrônica". A descrição do card irmão #7980 diz o oposto: "nesse primeiro momento não terá validação do número do MDF-e, segue conforme tipo de documento Outros".

Decidido em 05/08/2026 com o desenvolvimento, no #7980: vale a descrição — SEM validação. ConsistirAverbacaoRCV não foi alterado, e eu confirmei em tela que o mesmo documento curto é aceito com M exatamente como é aceito com O (CT-TDR-007 do #7980, aprovado em 07/08). Como o responsável do desenvolvimento é o mesmo, este plano não escreve CT de bloqueio de documento — escreve o CT de equivalência (CT-TDC-006), que é o que prova a decisão. Se Produtos quiser inverter a decisão para o CITNET, isso precisa vir explícito, porque criaria divergência de comportamento entre os dois sistemas na mesma regra.
