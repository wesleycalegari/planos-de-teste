Natureza do card (leia antes de executar): este PBI entrega a tela CITWEB de acerto manual da data de saída de DUIMPs retidas como Inconsistentes. A tela lê e grava tb_itf_smx_ctl_prc_dui (sts_prc, t_json_wi): lista as linhas 'I' e 'R', e ao salvar faz o replace da chave "DT_SAIDA" dentro do JSON gravado (parse/serialização) mudando o status 'I'→'R'. Quem CRIA linhas 'I' e quem REPROCESSA linhas 'R' é o worker IntegracaoWI — escopo do #8255 (plano próprio). Os oráculos deste plano são a tela (textos e badges exatos) e o banco HML (SQL read-only, consultas Q1–Q5 abaixo).
⚠️ Condições de execução: nenhum CT é executado antes da aprovação do plano (Gate 1 → Gate 2) e do DoD do dev (tela deployada em HML AXA — hoje o card está Stand by e a task de PR/HML #8319 em In Progress; a implementação foi validada só localmente pelo dev em 26/08). O CT-TDU-012 (E2E com reprocessamento automático) exige ADICIONALMENTE o worker do #8255 ativo em HML — sem ele, apenas esse CT fica BLOQUEADO por dependência externa (não herdar o bloqueio para os demais). Em 27/08/2026 a base HML AXA tem zero linhas 'I'/'R': a massa dos CTs de tela é semeada pelo contrato documentado (Pré-requisito 4), como o próprio dev fez.

2. Descrição

Hoje, quando a DUIMP chega sem data de saída, o worker a despreza definitivamente (sts_prc='D' — "Desprezada - DUIMP com data de saída inválida") e o operador precisa pedir à Quorum para reenviar, excluir ou recarregar o pacote. Com o par #8255 (worker retém como 'I') + #8256 (esta tela), o operador passa a: localizar as DUIMPs inconsistentes na nova tela do módulo Interface WI x Siscomex, informar a data de saída manualmente e deixar que o worker reprocesse sozinho no ciclo seguinte — sem tocar no pacote.

Contrato técnico verificado (fontes: mockup anexo ao card duimp_sem_data_saida_mockup_1.html, prints do smoke local do dev de 26/08, código da branch feat/ADO-8256-duimp-tela-acerto-sem-data-saida lido em 27/08/2026 e contrato de banco medido em 27/08 — os textos de tela serão reconfirmados in loco na execução):
• Listagem: SELECT ... WHERE sts_prc IN ('I','R') ORDER BY d_usu_inc — a tela mostra pendentes de ação ('I') E já corrigidas aguardando o worker ('R'); nunca o histórico de reprocessadas ('C' sai da lista).
• Colunas: Importador = chave "IMPORTADOR" do JSON; Data de Registro = d_usu_inc (dd/MM/yyyy); Data de Saída = chave "DT_SAIDA" do JSON (vazia quando null → linha 'I'); Status: 'R' → "Aguardando reprocessamento" (badge azul), senão "Inconsistente" (badge cinza).
• Filtro: por substring do número, case-insensitive (maxlength 15); placeholder Buscar por número da DUIMP.... Grid vazia: Não há DUIMPs sem Data de Saída pendentes de acerto! Contador: N DUIMPs inconsistentes (conta só 'I'). Paginação: 10 linhas por página.
• Painel de acerto: "Informar Data de Saída — DUIMP <nº>" com campo Data de Saída e botões Salvar/Cancelar — painel único, reaproveitado a cada "Selecionar" (garante o "apenas uma por vez" do card).
• Salvar: replace seguro via parse do JSON (DT_SAIDA = "yyyy-MM-dd") + UPDATE sts_prc='R' na(s) linha(s) 'I' daquela DUIMP, em transação.
• Mensagens exatas: obrigatório → Informe a data de saída. · data inválida/ano<1900 → Informe uma data válida · data futura → A Data de Saída não pode ser maior que a atual. · corrida/já corrigida → DUIMP não localizada ou já reprocessada. · sucesso → Ao salvar a Data de Saída, na próxima execução de carga a DUIMP será reprocessada.
⚠️ Deltas espec × implementação — para decisão no Gate 2 (Produtos):
D1 — Bloqueio de data futura: a implementação rejeita data de saída maior que a data atual ("A Data de Saída não pode ser maior que a atual.") — regra que não está no card nem no mockup (que só exigem ano ≥ 1900). Restrição adicional razoável, mas precisa ser formalizada por Produtos (CT-TDU-009 documenta o comportamento).
D2 — Janela de 2 anos da tela de DI não replicada: a tela irmã "DI sem Data de Saída" restringe a data a uma janela de 2 anos (exceto ACE/CHUBB); o dev registrou no código que NÃO replicou a regra para DUIMP — pendente de confirmação do PO se ela também se aplica aqui.
D3 — Painel único abaixo da grid: o card diz "a linha expande"; a implementação usa um painel único abaixo da grid, reaproveitado a cada seleção — atende o requisito funcional "apenas uma por vez" (registrado como equivalência aceita, salvo objeção de Produtos).
