📋 Contexto do defeito (PBI #7350 · TECSD-38734)

O quê: ao incluir DUIMPs para o importador GENERAL MILLS (CNPJ 61.586.558/0025-62, despachante Schenker), o CITWEB gravava as declarações na apólice expirada 0106220001985 (vig. 2023–2024) em vez da vigente 0106220002616 (vig. 31/08/2024–31/08/2025), impedindo o faturamento correto. Sistemático para todo pacote do Schenker.

Causa-raiz (código): em ObtemApoliceImportadorConsignatario, no ramo "faturamento pelo importador" (i_fat_prf != "C"), o método definia o segurado mas não retornava, caindo no fallback ListarComImportadorCossignatario (sem filtro de data, order by cd_apolice desc) que sobrescrevia a apólice já selecionada por data (ListarPorImportadorConsignatarioApoliceData(..., dataSaida)) pela apólice errada.

Correção: return new KeyValuePair<bool,string>(true, "") logo após definir o segurado — preserva a apólice selecionada por vigência. + log de exceção no catch. commit: 995e7371f · PR: 1345 / 1250 · branch: AXA_7350_DUIMP_HML.

ℹ️ Critério de Aceite (Cenário 4) coberto

  • Dado múltiplas apólices para o mesmo importador/subgrupo (histórico + vigente), quando associar uma DUIMP/DI, então a apólice selecionada deve ser aquela cuja vigência (início ≤ data de referência ≤ fim) contém a data de referência (data de saída / embarque = d_sda_vgm) — CT-ENQ-001, CT-ENQ-002.
  • Correção de código validada (early-return preserva seleção por vigência) — CT-ENQ-003.
  • Massa das apólices do card confirmada no ambiente — CT-ENQ-004.

⚠️ Limitações e transparência desta execução

  • Ambiente correto: o fix está no AXA comum (módulo WI build 260717.1712), não no Alfa — a validação foi refeita no comum.
  • O pacote exato do card (Schenker → General Mills) não pôde ser carregado: o arquivo PCK_43823079000244_...AXA (anexo do card) é binário criptografado e não há upload de pacote pela UII (só arquivo de filtro); o pacote não está na fila WI e a geração depende do WI-Quorum (sistema externo). Por isso o CA foi validado com um conflito natural equivalente já presente no ambiente (pacote Gladis, CT-ENQ-001) — mesma regra (apólice atual + anterior, seleção por data de saída).
  • A verificação foi feita a nível de dado (staging tb_itf_smx_dcl_pnd × vigência tb_apo_int_cit) + a mensagem do próprio sistema na fila — evidência mais forte que um PROTCARGA isolado.
  • Card em homologação paralela pela conta André Madeira (task 7819). Este plano é a verificação independente sob a conta do Wesley; não substitui o ciclo do André no AzDO.

CT-ENQ-001 Processamento completo (EFETUAR CARGA) de pacote com conflito de vigência: DIs enquadradas por data de saída P1 APROVADO ▾

Tipo

Positivo / end-to-end — processamento total (EFETUAR CARGA) de um pacote real cujo importador tem apólice atual e anterior, com declarações de datas de saída em ambas as janelas de vigência. É o CA Cenário 4 exercido no fluxo completo.

Pré-condições

  • CITWEB AXA HML comum · usuário FRED · módulo WI build V 1.0.260717.1712 (com fix)
  • Pacote 88037668000154 (Gladis, 30/01/2026) na fila DICarga — importador com apólice atual 5106220003349 (30/09/2025–30/09/2028) + anterior 5106220002017 (30/09/2023–30/09/2025)

Passos

  1. Login → Interface WI / Siscomex → Declarações Adições → Carga das Declarações do WI
  2. LISTAR PACOTES — o sistema sinaliza o pacote com a mensagem de vigência (atual/anterior)
  3. Selecionar o pacote e EFETUAR CARGA (confirmar "Sim") — processar todas as declarações do pacote
  4. Verificar no banco a apólice enquadrada (u_apo_pnc) de cada DI vs. sua data de saída (d_sda_vgm) e a vigência de cada apólice

Resultado Esperado

Processamento conclui e distribui as DIs entre as duas apólices conforme a data de saída: saída ≤ 30/09/2025 → apólice anterior; saída ≥ 30/09/2025 → apólice atual. Nenhuma DI fora da vigência da apólice em que foi gravada.

⛔ BLOQUEADO (dependência externa — WI-Quorum). Motivos confirmados: (1) o pacote PCK_43823079000244_20250702161234.AXA anexado ao card é binário criptografado (formato proprietário PCK12) — não é possível parsear/injetar seu conteúdo; (2) o CITWEB não oferece upload de pacote pela UI (o único arquivo aceito na DICarga é o "arquivo de filtro"); (3) o pacote Schenker não está na fila WI do ambiente e a relação/subgrupo do CNPJ General Mills não estão cadastrados. A ingestão do pacote depende do WI-Quorum (sistema externo legado), fora do alcance do QA — o .AXA só é decodificado pelo próprio WI durante a carga. O CA (seleção por vigência) está coberto pelo CT-ENQ-001 — processamento completo de um pacote de conflito equivalente (apólice atual + anterior, mesmo importador), gravado corretamente por data de saída. O método corrigido ObtemApoliceImportadorConsignatario é o mesmo caminho de seleção de apólice usado para DI e para DUIMP; validá-lo via DI exercita a mesma regra. Ressalva: o processamento do pacote Schenker/GM específico (DUIMP) só poderá ser homologado 1:1 quando o pacote for restaurado na fila do WI-Quorum.

Recomendação: para reproduzir o cenário idêntico, solicitar à equipe de integração/infra a restauração do pacote Schenker (cd_estabel=43823079000244 / 2025-07-02 16:12:34) na fila WI e o cadastro da relação/subgrupo do CNPJ GM.
