📋 Contexto da melhoria (PBI #7305)

O quê: o campo Lucros Esperados (%) aceitava no máximo 99,99% (2 dígitos antes da vírgula). O CIT VB6 aceitava 100%; a migração para o CITWEB não preservou essa capacidade, obrigando o time a usar 99,99% como contorno.

Correção: nova máscara dedicada mask-taxa3-2 (ZZZ,00, maxlength=6) no campo Lucros dos 3 formulários, com validação de teto ≤ 100 no cliente e no backend (AverbacaoProvisoriaDomain.Gravar e AverbacaoMovimentoAbertoInternacionalDomain.GravarDefinitiva). A máscara compartilhada mask-taxa2-2 (Frete/Despesas/Impostos) NÃO foi alterada.

PR: 1344 · commits: 9606a3c1b (fix), 9add627ab (testes), 60cc08167 (script DB) · branch: fix/ADO-7305-percentual-lucros-100

ℹ️ Critérios de Aceite cobertos

  • Campo Lucros aceita 100% na Averbação Provisória e demais formulários (CT-LUC-001, 005, 007)
  • Aceita 0% a 100% com 2 casas decimais / regressão de 99,99% e 0% (CT-LUC-003)
  • Recusa valores > 100% com mensagem clara (CT-LUC-002, 006, 008)
  • Demais campos percentuais (Frete/Despesas/Impostos) não impactados (CT-LUC-004)
  • Script de correção dos registros da apólice 1062206000249 sub 01-04 de 99,99% para 100% (CT-LUC-009)

⚠️ Observação — script de correção de dados (CT-LUC-009)

  • O script de migração ADO-7305-corrige-lucros-provisoria-apolice-1062206000249.sql (idempotente, com backup + rollback) foi executado em HML — a tabela de backup bkp_ado7305_avb_prv_lucros existe.
  • Em HML os subgrupos 001/002/003 estão em 100 e o 004 permanece em 99,99 — este é o fixture de regressão deixado pelo próprio dev ("exibe o contorno 99,99 corretamente").
  • A correção efetiva de dados legados 99,99→100 é etapa de RELEASE homologada por Produtos (DoD / CA do PO) — não exercida sobre dados legados em HML (backup vazio).
