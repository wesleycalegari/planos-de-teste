1. Descrição
Bug: No CITNET CHUBB, ao gerar o Resumo (ícone lupa) na tela Autorização de Prévia para Faturamento, a emissão do PDF da fatura falhava — "Problema está no momento da emissão da fatura". O fluxo aciona a função JS GerarResumo → POST /Relatorio/FaturaReportPdf → RelatorioController.MontaCorpoFaturaPDF(), que ao estourar grava ERRO ==> no log e propaga a exceção.
⚠️ Causa raiz exata NÃO isolada pelo dev (Ivan). Os 2 logs anexados ao card (LogErro14072026, LogErro17072026) não contêm o sintoma; um 3º log fornecido era o mesmo do #7872 (sem relação). A reprodução local com dados sintéticos (NSTECH) não reproduziu — o crash dependia de dado específico da apólice/segurado real do CHUBB (UAT). O dev confirmou que, após a nova versão, não reproduz mais, e validou em HML real; a mudança específica que resolveu não foi tecnicamente isolada.
Validação do dev (HML real, chubb-hml-faturamento.nsseg.com.br):
  • Ramo 21 (Transporte Nacional), apólice 100621002 → POST /Relatorio/FaturaReportPdf 200 OK, PDF "Resumo de Embarques - Apólice Mensal (Prévia)" gerado.
  • Ramo 32 (RCTR-VI, Internacional), apólice 100632002 → 200 OK, PDF "Relação de Embarques - Apólice Diária (Prévia)" gerado.
Natureza desta homologação: como a causa raiz não foi isolada, o reteste é do tipo "confirmar que não reproduz mais + o Resumo gera PDF válido". A evidência de aprovação é o próprio arquivo PDF gerado (não basta HTTP 200) — salvar, validar (não-vazio, header %PDF, conteúdo correto) e anexar.
2. Critérios de Aceite
  • CA1 — Na Autorização de Prévia para Faturamento, acionar o Resumo (lupa) para uma apólice CHUBB ramo 21 deve gerar o PDF sem erro (POST /Relatorio/FaturaReportPdf = 200, PDF válido), sem "Problema no momento da emissão" nem ERRO ==> no log.
  • CA2 — Mesmo cenário para ramo 32 (RCTR-VI) → PDF gerado corretamente.
  • CA3 — Regressão: geração do Resumo/relatório de fatura em outra apólice/ramo continua funcionando (sem quebra colateral).
